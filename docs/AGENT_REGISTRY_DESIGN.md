# 动态 Agent 注册、能力发现与版本绑定设计

日期：2026-11-05。状态：已 review，第一版核心实现已交付；下文保留设计及后续演进目标。

### 第一版实现边界

- 已实现 SQLite 草稿/不可变版本/活动指针/团队/任务绑定/调用记录，以及热注册、发现、回滚和退役。
- 已接入所有默认招聘槽位和可选专职检查槽位。专职发现必须有可定位原文引用，并进入评估与核查上下文；不直接淘汰候选人。
- 团队仅支持精确版本或跟随指定 ID 活动版本，运行开始后冻结。历史候选集合兼容读取；新团队不再配置候选池，不使用 LLM 自动选人。可靠执行队列见 [可靠执行层](RELIABLE_EXECUTION.md)。
- 契约采用平台目录中的固定 Schema；第一版不接收自定义 JSON Schema 或可执行验证器。FDE 扩展契约需修改目录代码。
- 知识访问角色及上下文预算、岗位对话读取权限、模型/工具限制已接入实际执行。长期规则提案写入仍只提供人工入口，不向 Agent 开放批准或写入工具。
- 独立试运行功能已按界面精简要求移除（含提交接口）；所有角色通过实际团队筛选或完成后对话验收。历史调用记录仍可查询。
- 模板代码由部署版本提供，定义快照不保存旧执行二进制。外部模型别名、MCP 服务实现与知识正文也不保证完整历史可复现。
- 第一版为单进程/单机设计：模型调用受 Agent 全局容量和超时信号约束；崩溃调用的容量租约到期后释放，不重放外部动作。退役不影响既有绑定和后续调用。

## 1. 目标与第一版范围

让 FDE 在不修改固定 Agent ID 列表、不重启服务的情况下，注册一个基于受控执行模板的新角色，按能力发现它，将其接入任务并追溯实际使用的版本。

第一版交付闭环：创建草稿 → 校验 → 注册不可变版本 → 激活 → 按能力发现 → 显式绑定 → 实际执行 → 监控追溯 → 退役。

支持多版本、回滚活动指针、在途任务快照、工具与记忆权限。暂不做分布式 Agent 网络、远程 A2A、任意代码上传、自修改 Agent、递归派生或通用工作流画布。

注册是管理能力，发现是选择能力；不能把“页面里多出一行配置”当作完成。验收必须运行一个新增角色。

## 2. 当前代码需要改变的地方

| 当前实现 | 改造方向 |
| --- | --- |
| `AgentId` 联合类型及固定 `AGENT_IDS` | 保留内置业务槽位类型，Agent 实体 ID 改为校验后的字符串 |
| `AgentRegistry.load()` 仅从配置读六个 preset | SQLite 持久化版本库；现有配置作为种子导入 |
| `capabilities` 是展示标签 | 引入受执行器、契约与权限约束的能力目录，参与筛选 |
| `new ParserWorker / AssessorWorker / AuditorWorker` 固定角色 | 槽位解析为确切 Agent 版本，再交给匹配模板执行 |
| 提示词按路径读取，缓存键仅 id/version | 注册时保存正文与哈希，缓存按完整版本哈希隔离 |
| 注册表指纹不覆盖提示词正文 | 版本哈希覆盖提示词、Schema、技能正文、工具声明及权限 |
| 完成后对话重新读取当前 coordinator | 读取 job 已绑定版本，避免对话中静默换角色 |
| 知识库依赖固定角色字符串 | 保留业务角色维度，增加可校验的知识访问角色映射 |

不要求一次把所有业务状态机改写为通用执行引擎。现有解析证据定位、代码重算分数、核查否决等确定性机制继续保留在内置模板中。

## 3. 概念分离

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| Agent ID | 稳定的逻辑实体标识 | `payment-assessor` |
| 版本 | 不可变的行为定义 | `1.1.0` |
| 实例 | 某次具体执行 | `invocation_xxx` |
| 业务槽位 slot | 工作流需要什么职责 | `assess`、`audit` |
| 执行模板 template | 平台如何运行并验证输出 | `builtin.assessor.v1` |
| 能力 capability | 可供任务筛选的结构化声明 | `resume.assess@1` |
| 契约 contract | 输入输出的语义与结构要求 | `recruitment.evaluate@1` |

显示名称、角色说明、能力声明不能直接授予工具、知识库或记忆权限。同名 Schema 也不能自动证明业务兼容，需要显式契约 ID 与版本。

## 4. Agent 定义

建议的定义结构如下，字段按执行模板收窄，避免任意组合产生不可执行配置：

```ts
interface AgentDefinition {
  id: string;
  version: string;
  name: string;
  description: string;
  roleTags: string[];

  executor: {
    templateId: string;
    templateVersion: string;
  };
  capabilities: { id: string; version: number }[];
  inputContract: string;
  outputContract: string;
  prompt: { content: string; hash: string };
  skills: { id: string; version: string; content: string; hash: string }[];
  modelPolicy: { tier: 'flash' | 'pro' };

  tools: { id: string; contractVersion: string }[];
  mcp: { pluginId: string; tool: string }[];
  knowledge: { accessRoles: string[]; maxContextChars: number };
  memory: {
    read: ('job-profile' | 'job-decisions' | 'job-chat' |
           'candidate-evidence' | 'approved-policies')[];
    write: ('task-result' | 'policy-proposal-draft')[];
    scope: 'job' | 'candidate';
  };
  limits: { maxConcurrency: number; timeoutMs: number; maxToolSteps: number };
}
```

实现要求：

- ID 使用受限格式，版本使用可校验的三段数字；不靠字符串排序比较版本。
- 定义文档有独立 `schemaVersion`，不要和 Agent 行为版本混用。
- 定义中不保存 API Key、MCP 凭据、任意文件系统路径或动态 import 地址。
- 模型 tier 在任务启动时解析为实际提供商/模型 ID 并记录；外部模型别名变化仍无法保证输出完全复现。
- 新增角色默认无工具、无 MCP、无知识访问、无长期记忆写入权，子角色默认不可委派。
- 即使允许 `policy-proposal-draft`，也只能创建待审草稿；长期规则的批准权永远不授予 Agent。
- 知识访问角色由管理员在注册时选择并校验，任务不能通过自报角色扩大检索范围。

## 5. 受控执行模板

| 模板 | 用途 | 边界 |
| --- | --- | --- |
| `builtin.profiler.v1` | JD 与评分卡生成 | 保留澄清、受保护条件处理与版本复用确认 |
| `builtin.parser.v1` | 简历解析 | 保留引用定位和结构化校验 |
| `builtin.assessor.v1` | 初筛、深评、反馈重评 | 保留固定评分卡、代码计分与阈值 |
| `builtin.auditor.v1` | 证据和合规核查 | 保留机制层否决与人工升级 |
| `builtin.coordinator.v1` | 规划与完成后对话 | 保留工具审批与流程执行边界 |
| `builtin.ingest.v1` | 文件接入 | 确定性处理器，不宣称为 LLM Agent |
| `structured-llm.v1` | 新增专职检查角色 | 只生成结构化结果，无工具循环，输出需满足选定契约 |
| `tool-agent.v1` | FDE 新增工具型助手 | 只调用授权工具，有步数/时限，复用现有审批，不自动委派 |

模板在代码中注册，由 FDE 扩展。平台运行时注册 Agent 定义，不加载上传的任意代码。

输入/输出 Schema 第一版使用平台支持的注册契约。专职检查可使用受限的声明式 JSON Schema 子集；禁止远程 `$ref`、自定义可执行校验器以及无界结构。JSON Schema 校验通过不等于证据校验通过。

内置业务槽位只接受对应语义契约与模板族，不能用一个“输出长得相似”的通用 JSON Agent 替换核查器，从而丢失确定性否决。

## 6. 版本与生命周期

草稿允许编辑，使用 revision/ETag 防止多人覆盖；注册后生成不可变版本及内容哈希。

```text
草稿 → 校验成功 → 注册版本（inactive）
                         ↓ 激活
                    活动版本 active
                         ↓ 退役
                    retired（不接新任务）
```

活动版本通过独立指针表示；同一 ID 最多有一个活动版本。激活新版本只移动指针，旧版本保持可查询、可绑定在历史任务上。

区分两种操作：

- **取消激活**：新任务不再默认选择；历史任务继续。
- **退役/注销版本**：软注销，不再供新任务发现或选择；已绑定任务正常续跑。

回滚是将活动指针切回一个未退役的旧版本，不覆盖版本正文。删除草稿允许物理删除，注册版本保留历史。

第一次启动导入现有六个 preset。以后修改 `config/agents.json` 或提示词文件，不自动覆盖数据库中的已注册版本；提供显式“预览导入差异 → 创建新版本”。

## 7. 能力发现与选择

```ts
interface AgentQuery {
  capabilitiesAll?: string[];
  capabilitiesAny?: string[];
  roleTags?: string[];
  inputContract?: string;
  outputContract?: string;
  templateFamily?: string;
  tier?: 'flash' | 'pro';
}
```

发现分两层：

1. **静态可用性**：已激活、未退役、能力兼容、契约兼容、模板存在、工具和权限声明合法。
2. **运行时可执行性**：当前提供商可用、工具已连接、实际权限仍允许、容量有空闲。

查询返回确切版本和命中理由，也返回不可选原因供管理页面排查。`eligible` 与 `ready` 分开，暂时满载不等于未注册或能力不匹配。

能力不能只靠填写字符串通过：模板必须支持对应能力，契约必须兼容，所需工具必须实际实现。额外领域标签如“支付经验”仍属于声明，平台不能保证模型真实专业水平；质量通过实际运行及评测判断。

能力发现用于开发者按能力查询，再显式绑定团队角色。规划器只影响批次、并发与深评路径，不选择或替换 Agent。无合适绑定时明确报错，不回退到权限更大的角色。

当前提供持久化资源等待及简单可选优先级，不建设最优负载路由、Agent 自动比较或分布式派发。

## 8. 注册后如何实际进入招聘流程

第一版提供两条路径：

### A. 替换已有槽位

建立版本化团队配置，例如：

```ts
{
  id: 'payment-recruiting',
  version: '1.0.0',
  slots: {
    profile: { agentId: 'profiler', version: '1.0.0' },
    parse: { capability: 'resume.parse@1' },
    assess: { agentId: 'payment-assessor', version: '1.0.0' },
    audit: { capability: 'resume.audit@1' }
  }
}
```

精确绑定用于可控交付；能力绑定用于在合格候选中选择。任务创建时解析全部实际版本，不能每处理一份简历就读取活动指针。

### B. 增加一个受控专职检查节点

提供可选 `specialist-check` 扩展槽位，位于解析之后、初筛之前。新角色可使用 `structured-llm.v1` 完成资格或行业要求检查。

输出固定为 `findings[]`，包含检查代码、说明、严重程度和当前候选人的证据引用。证据由代码验证，结果保存到该调用的任务产物，并传给评估/核查作为参考。

默认不能直接改变评分卡、自动淘汰候选人或跳过核查。需要新增强制审批、复杂分支或其他业务顺序时，由 FDE 扩展明确的业务适配器，后续再接通用工作流接口。

这一扩展槽位让新增资格核查角色真正参与筛选，避免只有配置管理、没有执行入口。

## 9. 运行绑定、记忆与权限变化

每个 job 保存不可变 `AgentManifest`：团队版本、槽位到确切 Agent 版本的映射、定义快照及哈希、提示词/技能/契约哈希、解析后的模型配置、模板兼容版本。

每次调用记录：job/run/node、slot、agent ID/version/hash、实例 ID、模板、模型、输入输出引用、usage、审批引用及失败原因。报表同时保留业务槽位与实际角色名称，不能继续把所有调用硬记成 assessor。

续跑和完成后对话使用已绑定清单。激活、回滚或普通退役不改变旧任务。当前权限可收紧，实际授权为“任务快照允许 ∩ 当前平台允许”；不能因为旧快照允许某工具就绕过当前禁用。

工具 Schema 或语义契约变更时，不沿用旧批准。代码模板版本不可用时明确阻塞，提供人工迁移说明，不能假装老执行器仍然存在。

记忆和知识库采用以下规则：

- 冻结访问策略和评分卡版本，记忆内容仍随当前任务的合法决策增长，不冻结整个聊天数据库。
- 候选人级 Worker 只能读取当前 job + 当前 resume 的证据；从执行上下文取得 ID，忽略模型提供的其他 job ID。
- 新角色必须显式配置知识访问角色；取消知识库启用或收紧权限即时生效。知识文档内容不在本次设计中整体版本化，因此不能承诺其历史全文可复现，调用时记录命中文档/片段引用和哈希。
- 已有 L3 规则发布仍通过人工管理入口；注册一个带“审批能力”标签的 Agent 不能获得批准权。

## 10. 持久化结构

沿用主 SQLite 台账及审计事件，建议新增：

| 表 | 用途 |
| --- | --- |
| `agent_drafts` | 可编辑草稿、revision、来源版本 |
| `agent_versions` | ID/version 唯一、完整定义、内容哈希、注册人和时间、退役/撤销状态 |
| `agent_active_versions` | ID → 活动版本指针，乐观并发更新 |
| `agent_teams` | 不可变团队版本及槽位绑定策略 |
| `job_agent_manifests` | job 清单快照与哈希 |
| `agent_invocations` | 每次调用的确切角色、版本、槽位与结果索引 |

模板、能力及契约目录第一版由代码注册，提供只读目录接口；不增加可执行代码上传接口。

活动指针更新、版本状态修改与事件写入在同一事务中完成。注册同 ID/version 同内容应幂等返回；不同内容返回冲突。更新指针必须带预期 revision。

## 11. 界面和 API

侧栏新增“Agent 团队”，避免把主要管理能力藏在环境自检中。提供角色列表、详情与版本、团队配置、任务绑定和运行检查视图。

创建角色时选择模板，以表单配置说明、提示词、技能、模型、知识和记忆权限；展示模板限制与输出契约。保存草稿后可校验，再人工注册/激活。注册新定义本身不执行模型或工具；验证通过实际团队运行完成，产生可审计调用并遵循工具审批。

新建会话选择团队（默认内置团队），展示本次确切角色版本；专业检查节点是可选项。界面沿用现有简洁布局，默认折叠高级配置。

API 草案：

| 接口 | 行为 |
| --- | --- |
| `GET /api/agent-catalog` | 模板、能力、契约及权限目录 |
| `POST/PATCH /api/agent-drafts` | 草稿创建和带 revision 的修改 |
| `POST /api/agent-drafts/:id/validate` | 返回校验结果，不激活 |
| `POST /api/agent-drafts/:id/register` | 注册不可变版本 |
| `GET /api/agents` | 查询/按能力发现，返回确切版本与状态 |
| `GET /api/agents/:id/versions` | 版本历史 |
| `POST /api/agents/:id/activate` | 带预期指针版本激活/回滚 |
| `POST /api/agents/:id/versions/:version/retire` | 软注销 |
| `GET/POST /api/agent-teams` | 团队查询和版本注册 |
| `GET /api/run/:jobId/agent-manifest` | 查看该任务实际绑定 |

管理接口不进入模型工具池。维持当前本地单用户部署边界，不把“服务端填写操作者”称为企业身份认证。

## 12. 兼容与实施顺序

1. **注册表与版本库**：引入新类型/Schema、数据库及只读目录，幂等导入现有 preset；旧接口保留兼容适配。
2. **动态发现与管理界面**：草稿、校验、注册、激活、退役、团队定义与条件查询。
3. **执行绑定改造**：job 清单、模板适配器、实际角色元数据、提示词缓存隔离、旧任务续跑与对话绑定。
4. **专职节点与记忆接入**：新增角色真实参与流程，复用证据校验、工具审批、知识和记忆边界。
5. **迁移和验收**：新旧流程回归、并发注册/激活、版本失效场景、HTTP 与界面验证、FDE 扩展指南。

旧 job 若没有清单，在首次恢复时创建“迁移时绑定”快照并标记绑定时间；不能把当前配置说成该 job 历史上真正用过的版本。缺少原始定义时展示历史未知，不伪造可复现性。

## 13. 验收清单

- 服务运行中注册一个新资格检查角色，无需改 ID 联合类型或重启；按能力发现并真实执行。
- 同 ID 多版本并存；同版本不同内容被拒绝，重复同内容注册幂等。
- 未知模板、无效契约、能力与执行器不兼容、未实现工具、越权记忆声明均被拒绝。
- 激活 v2 后，新任务用 v2，旧任务和后续对话仍用 v1；回滚只影响后续任务。
- 退役停止新任务使用，不破坏已绑定任务。
- 两个客户端并发激活不会静默覆盖；数据库故障时状态和审计一起回滚。
- 相似结构但不同语义契约不能替换核查槽位；专职检查不能绕过证据与人工决策。
- 角色名称变化后，日志、成本、报告和任务详情正确显示实际 ID/version，而非固定旧名称。
- 实际工具调用都遵循模式审批，参数/契约变化后旧授权无效。
- 模型伪造 job ID、角色或 capability 时，不能跨岗位读取或获得批准权。
- 注册/激活后刷新页面和重启服务仍保留状态；未注册的草稿不进入发现结果。
- 默认团队的现有筛选、Self-Loop、暂停续跑、评分卡记忆和导出测试全部通过。

## 14. 建议 review 时确认的三项范围

1. 第一版同时支持内置槽位替换和一个可选专职检查槽位；不在本次建设通用工作流引擎。
2. 由用户选择团队，每个角色固定绑定一个版本；能力查询供开发者配置使用，运行中不自动改派。
3. 注销保留在途任务，继续使用已绑定的 Agent 版本。

以上范围已 review；第一版使用步骤与实际配置格式见 [Agent 扩展指南](AGENT_EXTENSION_GUIDE.md)，实现边界见本文开头。
