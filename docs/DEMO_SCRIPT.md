# 8 分钟演示脚本

> 目标：在 8 分钟内完整展示"HITL → 扇出解析 → 评估-核查自环 → 汇总 → 终稿确认"，并让评委看到**失败路径**与**可复现证据**。
> 建议提前执行一次 `pnpm demo:auto --fresh` 预热（生成依赖索引），正式演示用交互模式或 `--yes` 均可。

## 准备（30 秒，不计入）

```bash
cd bole
pnpm install        # 首次
pnpm seed           # 20 份黄金简历
pnpm bole doctor    # 证明环境就绪：20 封邮件、7 个 Agent、台账可写
# 可选：浏览器演示（HITL 点选、实时事件、多视图报告）
pnpm web            # http://127.0.0.1:8787
```

窗口建议：左侧终端跑命令，右侧编辑器/浏览器打开报告。字号调大，`NO_COLOR=1` 可避免录屏时颜色过亮。

---

## 0:00–0:30 开场：问题与定位

> "招聘初筛有两个硬问题：结论没有出处，出了问题无法回溯；以及筛选过程可能无意使用性别、年龄等受保护属性。伯乐不是'让 LLM 写一段推荐语'，而是把每次判断都变成可核查的证据链，并在关键节点让 HR 签字。"

同时展示终端：`bole agents` 输出 7 个 Agent 的档位、深度预算与 schema。

## 0:30–1:30 HITL-1：需求疑点反问

```bash
pnpm demo
```

看到第一个反问：

```
【HITL 需要你确认】jd_clarification
薪资为"面议"。平台是否需要按固定区间筛选候选人？
  1) 不限薪资，仅作参考（推荐）
  2) 按 40-60K 区间筛选
  ...
```

话术：
- "注意这不是让 HR 重写 JD，而是把不可判定的条件变成可选项。"
- 选推荐项；随后团队规模、受保护属性两条依次确认。
- "最后一条很关键：需求里写了'限男性、30 岁以下'。平台没有把它偷偷变成评分维度，而是**剥离 + 记录 + 让 HR 确认**。这条会进合规报告。"

预期事件：`jd.analyzed` 显示 `剥离受保护条件 2 项`。

## 1:30–2:30 接入：20 份简历、去重与格式归一

事件流会滚动出：

```
R01 接入成功（docx, 210 字符）
...
R18 判定为重复投递（与 R05 一致）
R19 接入失败：P0 不支持该格式：doc（P0 仅支持 docx，请另存为 docx）
简历接入完成：成功 18，重复 1，失败 1
```

话术：
- "19 份可处理，1 份重复被拦，1 份旧版 doc 如实失败——失败明细会进报告，不静默丢弃。"
- 强调唯一入口：`resume_id` 进台账，其他 Agent 不能再碰邮箱。

## 2:30–4:00 解析扇出 + 批流动

观察事件：
- 多份 `解析开始` 同时出现（解析池 4）；
- `第 1 批完成` 之前，`第 2 批` 已经开始解析（无全量屏障）；
- `解析完成` 后立刻出现 `评估开始`，全部候选人都先走 flash 初筛；
- 初筛后出现 `深评短名单：N 人（Top 40% + 异常，pro）`，只有短名单进入 pro 深评。

话术：
- "每个字段的引用不是模型编的 offset：模型只给原文 quote，平台用字符串定位计算字符区间；定位不到就同轮重试。"
- "解析失败的简历不阻塞整批。"
- "扇出阶段用 flash 控成本，短名单才升级 pro——这是按任务难度分配档位，不是按职级。"

可在另一个终端跑：

```bash
pnpm bole status --events 40
```

展示台账状态与池统计。

## 4:00–6:00 评估-核查自环（演示核心）

关注 R17：

```
R17 flash 初筛完成：80.5 分（yes）
R17 pro 深评完成：80.5 分
R17 核查裁决 re_eval（2 条未通过）
R17 验真环打回重评 第 1 轮（沿用 assessor-deep#N）
续用同一评估 Worker：assessor-deep#N
R17 评估完成：76.5 分（yes，pro/revise）
R17 核查裁决 pass
```

话术：
- "监军发现：结论写'主导过千万级日活系统架构设计'，但原文只有'参与支付系统开发'——这是模型幻觉，被打回。"
- "打回不是新起一个 Agent，而是**续用同一个 Worker**，带着驳回意见修正；台账里 revision_of 指向上一个版本。"
- 然后看 R16：

```
R16 核查裁决 re_eval（3 条未通过）
...
R16 核查裁决 escalate_human（1 条未通过）
R16 转人工：验真环已达上限（2/2）
```

- "证据稀疏的简历，两轮重评仍然举证不了，平台不会硬凑一个结论，转人工。"
- 再看 R20：

```
R20 核查裁决 escalate_human（0 条未通过）
R20 转人工：公平性哨兵：评估理由使用了受保护属性
```

- "这一条 0 条证据不通过，但评估理由里出现'年龄偏大'——公平性哨兵直接拦截。合规不是报告末尾的一句话，是运行时机制。"

现场审计（可选，若时间允许）：

```bash
pnpm bole audit --resume R17
```

展示字段 span → 评估 → 两轮核查逐条 verdict。

## 6:00–7:00 汇总与 HITL-2

最后一条 HITL：

```
已生成 Top5 推荐、证据链与合规报告（16 人核查通过，2 人转人工）。是否确认输出终稿？
```

选"确认输出终稿"。随后：

```
Top 候选人
  1. R01 89.0 strong_yes
  2. R05 87.0 strong_yes
  3. R11 80.0 yes
  4. R03 79.5 yes
  5. R15 79.5 yes
```

打开 `runs/<runId>/report.md`（或 `report.html`）：
- 每人一张维度表；
- 证据链表格：结论 → 原文引用 → 字符区间 → 核查状态；
- 面试建议锚定具体引用；
- 合规报告：受保护条件剥离、重复投递、失败明细、核查否决率；
- HITL 决策表（含 actor）。

话术："终稿确认不是走过场：未确认时报告状态是草稿；确认动作与回答写入 decisions 表。"

## 7:00–7:40 成本、调度与缓存

```bash
pnpm bole cost
```

展示按 Agent 的 token/成本，以及：

```
合计: ... 输入 / ... 输出 / ... 缓存命中（约 24%）/ $0.114
详细缓存对比见 runs/<runId>/cost-report.md
```

话术：
- "flash/pro 分工：解析、接入与评估初筛走 flash；短名单深评、核查、画像与面试建议走 pro。"
- "Top40% + 异常样本才深评，pro 评估调用从'全量 21 次'降到 15 次；简历越多，这个比例优势越明显。"
- "批量扇出时，系统提示词+评分卡+工具池作为共享前缀，差异内容只放末尾；cost-report 里对比了有无前缀对齐的实测成本。"
- "调度不是越多并发越好：池统计显示峰值与拒绝次数，拒绝后由编排层有界重试，而不是无限排队。"

可选：

```bash
pnpm bole bench
```

展示并发 1/4/8 的吞吐、P50/P95，说明这是调度层微基准，不含真实推理时延。

## 7:40–8:00 收尾：可复现与边界

```bash
pnpm test:all
```

看到 42 个测试通过。

话术：
- "黄金集 20 份固定简历、固定 Message-ID、固定 seed；Top5 与陷阱样本行为都冻结在 `data/golden/expectations.json`，`pnpm test:golden` 每次校验。"
- "我们没有做的也写清楚了：真实 IMAP、事务级恢复、PDF 扫描件、LLM-as-judge 五维评测、真实档位质量 A/B 都在 P1；默认 mock 是规则模拟，不代表真实模型效果。"
- "平台只出建议，不生成 offer/拒信。这是产品边界，也是合规要求。"

## 备用方案（若现场异常）

| 异常 | 处理 |
|---|---|
| 交互终端卡住 | 改用 `pnpm bole demo --yes --fresh`，自动 HITL 并记录 actor |
| 端口/网络异常 | mock 模式完全离线，无需网络 |
| 想看已生成报告 | `runs/<runId>/` 下直接打开 `report.md` / `report.html`；`pnpm bole report` 打印路径 |
| 想重放同一结果 | 固定 seed + mock；重新 `pnpm bole demo --yes --fresh` 可得到相同 Top5 与状态计数 |
| 时间不足 | 跳过 `audit` 与 `bench`，保留 R17 自环与 R16/R20 转人工三段 |
