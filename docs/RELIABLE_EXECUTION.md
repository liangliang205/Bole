# 可靠执行层与 Agent 分配收缩

本次目标是降低实施和维护成本，改善执行可靠性，不建设通用智能选人系统。

## Code review 结果与处理

| 发现 | 处理 |
| --- | --- |
| 能力候选实际上只是排序后取首个，没有负载路由收益，却增加配置与说明成本 | 新团队每个槽位只允许一个精确版本或指定 ID 的活动版本；创建运行时冻结确切版本。能力发现保留为开发者查询工具 |
| 旧团队已经保存候选列表，直接删除会破坏已有配置 | `storedTeamSchema` 仅兼容读取历史定义，沿用原稳定选择；新建/修改团队必须改为单个绑定，不改写旧版本 |
| 容量等待为会话内存队列，多个会话不能统一协调 | 新增 SQLite `execution_queue`；平台、岗位、阶段及确切 Agent 版本按资源键统一准入 |
| 工作流节点的 running 状态无法解释是在等容量还是调用模型 | 队列单独记录 queued/running/succeeded/stopped/interrupted、等待原因、执行次数；在原工作流面板内折叠展示 |
| 恢复租约只限制进入，旧执行者失去租约后仍可能写回结果 | 节点执行前后校验根运行所有权；失去租约不覆盖节点、运行或新执行者预留，不释放他人的租约 |
| 候选人阶段失败但业务记录仍停在 parsed/evaluated，collect 可能缓存不完整结果 | 非终态执行异常向上传播为可解释暂停，在聚合成功前停止；保留已提交业务结果并通过检查点恢复 |

## 保持简单的职责划分

- 工作流：唯一负责依赖、条件、循环、人工审批和结果检查点。
- Agent 注册表：唯一负责角色、技能、权限及版本绑定。
- 执行队列：仅负责已到达执行点的任务何时获得资源，不重新规划依赖，也不保存第二份任务输入/输出。
- LLM 规划器：保留批次、并发和深评建议，不新增高频 LLM 排队决策。

任务尚未到达的工作流步骤不会预先展开为另一套 DAG。恢复时重新进入原节点，由稳定的节点路径定位队列项。数据库队列没有独立守护进程；重启后仍使用已有“续跑”入口恢复，不能仅凭数据库里有待办就自行运行。

## 最小 FDE 接口

```ts
const result = await ctx.schedule(
  'assess:candidate-id',
  [
    { key: 'platform:agents', capacity: 8 },
    { key: 'job:job-id:assess', capacity: 2 },
    { key: 'agent:assessor@1.0.0', capacity: 4 },
  ],
  () => executeBusinessTask(),
);
```

`ctx.schedule` 必须在工作流节点中使用。一个稳定的 `runId + nodePath + label` 对应同一队列项；恢复不能偷偷改变资源约束。持久化的是调度元数据，真正输入和结果由工作流与业务台账保存。不要将包含子节点或人工等待的整个控制流程包装在资源预留中。

默认普通优先级、FIFO；可选第五个参数 `0 / 1 / 2` 为低/普通/高。等待每满一分钟提升一档，到高为止；同档按原入队顺序。优先级只影响未开始且可获得资源的任务，不抢占模型请求，不修改招聘分数。第一版不另建优先级管理界面或 Agent 适配度评分器。

资源按同一事务一起检查和预留，不先拿一半再等待另一半。不同运行若对同一资源声明不同容量，遵循当前预留中较保守的上限；平台容量应由统一配置管理，不能把每个会话的 LLM 建议当作不同的平台上限。

招聘主处理流程通过队列执行解析、专项检查、评估、核查与修正。画像、规划和 OCR 等未处于 Worker 预留中的工作流模型请求由 LLM Router 自动接入同一队列，只预留模型请求时间，不占用人工问答等待时间。对话模型不属于工作流队列，但仍受 Agent 调用容量约束；队列会计入这些外部调用。

模型调用记录保存 `executionId`，从而把同一 Worker 的执行预留与真实模型调用关联，不能算成两份 Agent 负载。旧 `CapacityPool` 在招聘适配器中仅提供已有报告兼容的本地统计，不再承担排队、重试或超时决策。

## 暂停与恢复

- 等容量不算失败、不增加执行次数；不会因等了固定 30 秒就跳过材料。
- 暂停停止新派发，在途请求收束；正在等待的节点持久化停止原因。
- 根运行租约失效后，旧预留不再占容量；面板显示等待恢复，而非假装一直执行中。
- 恢复复用队列项和工作流成功结果，安全任务沿用已有业务结果重建机制。
- 外部副作用不确定时保留原 `waiting_confirmation` 机制；调度器不能自动批准或重放。
- 暂不提供自动网络重试策略、自适应路由、分布式 Worker、抢占或 exactly-once 保证。

执行队列不会解决不完整业务输入、模型持续输出非法内容或模板版本不兼容。报告生成与发布仍必须通过候选人终态完整性检查，不能因为队列暂时空了就认定筛选完成。

## 版本与验收

招聘参考流程发布为 `1.3.0`。保留历史任务与团队，不能让旧运行静默切换到新源码；没有保留兼容实现的旧流程需要明确处理，而不是修改历史绑定哈希。新建会话使用本次实现。

主要回归：

- `tests/unit/execution-scheduler.test.ts`：跨会话容量、等待不计失败、优先级/老化、暂停、数据库重开、过期租约、重复入队、外部 Agent 调用计数与写回隔离。
- `tests/unit/agent-platform.test.ts`：新单一绑定、历史候选定义兼容。
- 招聘集成测试：真实执行路径中的画像、规划、核查均产生队列记录；人工等待不占模型容量；成功结果恢复不重复执行。
