# 已知限制与边界

> 这份文档只列**当前真实限制**。已移除的 mock/黄金集/HTML 报告不再作为"限制"出现。

## 1. 简历接入

| 项 | 当前行为 | 边界 |
|---|---|---|
| 来源 | 仅用户上传（API/UI/CLI `--files`） | 不做 IMAP/Exchange 邮箱拉取；没有 mock 邮箱 |
| 格式 | PDF（文本层）、DOCX、TXT、MD、HTML、PNG/JPG/WebP/BMP/TIFF | 旧版 `.doc` 明确拒绝，提示另存 docx |
| PDF 扫描件 | 文本层为空时直接报错，提示上传图片 | 未做 PDF 页面渲染后 OCR（需要 canvas；P1） |
| 图片 OCR | 默认 DeepSeek V4 Flash Vision；失败或 BMP/TIFF 回退本地 Tesseract | Vision 仅支持 JPEG/PNG/GIF/WebP；手写体、低分辨率、复杂版式仍可能出错；图片 token 计入成本；图片会以 base64 发送给 DeepSeek API，不能外发时用 `BOLE_OCR_MODE=local` |
| 语言数据 | `pnpm ocr:download` 下载到 `data/ocr`，已 gitignore | 未下载时图片简历失败并给出提示；Docker 镜像构建时下载 |
| 单文件大小 | ≤25MB | 大文件 base64 传输会占用内存 |
| 附件数量 | 支持多文件上传 | 每份文件独立成一份简历；不做一封邮件多附件聚合 |
| 去重 | 同 job 内 sha256 + 身份指纹（姓名/手机/邮箱归一化） | 跨岗位重复投递不抑制；身份缺失时退化为正文指纹，可能漏判 |

## 2. 知识库

- **格式**：知识库文档复用简历归一化链路，支持 PDF/DOCX/TXT/MD/HTML/图片；暂不支持 PPTX/XLSX/EPUB。
- **默认关闭**：知识库创建后默认 `enabled=0`，不启用就不参与画像/评估/建议；没有内置知识库。
- **检索模式**：未配置 embedding 时使用中英混合 token 关键词检索；配置 Ollama/OpenAI embedding 后才做向量混合检索。embedding 服务不可用时自动退回关键词。
- **分块设置**：`chunkSize`/`chunkOverlap`/`smartChunk` 只影响新上传文档；修改后不会自动重切已有文档，需要重新上传。
- **范围**：当前只有“全局启用知识库”，没有 DSH 的项目/会话逐次挂载；不做笔记、工作日报和回答后自动回写。
- **凭据**：知识库的 embedding/rerank API Key 存在 `data/knowledge.db`，未使用模型提供商那套 AES 加密；请保护该文件权限。

## 3. 模型与质量

- **真实 API 必需**：没有可用模型提供商 Key 时 `bootstrap` 立即失败；产品路径没有 mock 回退。Key 不从环境变量读取。
- **模型非确定性**：温度=0 仍可能有 ±1 分波动；同一批简历重跑 Top5 可能变化。
- **流式 structured 输出**：token 先进入前端"实时生成"，最终仍以完整 JSON 的 schema 校验 + 两阶段提交为准；无效输出会重试，前端可能看到一段被丢弃的 token。
- **流式 usage**：DeepSeek 通常返回最终 usage；若网关不返回，成本按 `estimateTokens` 估算，不是账单精确值。
- **成本**：成本表按模型名查价；自定义提供商的模型若未在 `config/pipeline.json#pricing` 配置，会使用 DeepSeek Flash 费率兜底，成本仅供参考。
- **自定义提供商模型目录**：可通过「获取可用模型」从网关拉取；OpenAI 使用 `/v1/models`，阿里云百炼 MaaS 使用 `/api/v1/models`，不支持这些接口的网关可手动添加模型 ID。
- **Qwen/Ling thinking**：自定义千问/百炼模型默认发送 `enable_thinking=false`，避免推理 token 吃满结构化输出预算；结构化任务默认 8192 输出 token，遇到 max-tokens 会翻倍重试一次（上限 32768）。
- **质量未做真实 A/B**：flash/pro 的分层是工程策略（扇出用 flash、判断/否决用 pro），没有"分档一定更好"的量化结论；需真实 Key + 人工标注重复实验。
- **未接入 LLM-as-judge**：没有五维 LLM 评分、P/R/F1、NDCG、kappa。

## 4. 编排与恢复

- 统一子 Agent 总上限由 `maxActiveAgents` 控制（默认 8，Agent 可在 1–12 内调整）：`withAgentSlot` 同时抢"全局名额 + 阶段名额"，满载时退避；与阶段池一样有 30s 准入超时，极端情况下会导致任务失败。
- 筛选计划由主 Agent 决定，每次运行多一次 pro 规划调用（约 2–3k 输入 token）；Agent 不可用或输出不合法时回退配置默认值，不会阻塞流水线。计划本身可能不是最优，skill 文案与边界是主要调节手段。
- 完成后追问的 flash/pro 档位选择是**启发式**（问题长度/关键词/是否有附件或文件操作），不是模型判难；过于隐晦的复杂问题可能被判到 flash，影响深度。
- 完成后追问只由主 Agent 处理，不派生额外子 Agent；多 Agent 扇出仅用于多简历筛选。
- 容量池满时**直接拒绝 + 退避重试**，不维护全局队列；准入超时为 30s，两个批次同时在途时对同一池的瞬时需求可达容量的 2 倍，饱和时会出现 `PoolFullError`，个别解析/初筛任务失败（真实运行台账中已观察到）。调大池容量或准入超时可缓解。
- 批流动避免全局 barrier，但单批内仍按解析→初筛→深评→核查顺序推进；`review` 池容量默认为 1，核查全局串行，是批量吞吐的主要瓶颈。
- 检查点续跑覆盖批次与任务级；不做 SQLite 事务级崩溃一致性保证。
- 核查/深评输出被 `max-tokens` 截断时只翻倍重试一次；长简历的逐条核查可能因此失败并进入 `failed/quarantine`。
- HITL 在 Web 中只保存在当前服务进程内存；服务重启后，运行中的 HITL 问题会丢失，需要从检查点续跑重新触发。
- 运行中的 SSE 连接不跨进程恢复；刷新页面会重新连接当前 job（如果服务仍在运行）。

## 5. 前端与部署

- 单机单用户设计；默认只监听 `127.0.0.1`，没有登录、权限、多租户。
- Key 由服务端 AES-256-GCM 加密持久化在 `data/keyring.*`；同一数据目录下的所有浏览器共享该绑定。主密钥与密文在同一文件系统，属于本机文件保护级别，不是 HSM/KMS；生产应换用密钥管理服务。
- 没有浏览器级 e2e 测试；UI 通过静态检查、HTTP 冒烟与手工使用验证。
- 报告只有 Markdown + JSON（+ 成本报表/收敛 SVG），**没有 HTML 报告**。
- 成本页的 token 统计来自台账 `usage` 表；流式估算与真实账单可能有差异。
- Docker 容器内监听 `0.0.0.0:8787` 且 compose 发布端口；应用本身没有登录，直接暴露到局域网/公网等于无鉴权。只在本机使用时请把端口绑定改成 `127.0.0.1:8787:8787`。
- 完成后对话的 `python_exec` 在子进程执行任意 Python，没有沙箱；简历内容与 MCP 返回是不可信输入，存在间接提示注入 → 本地代码执行的风险。`export_word` / `office_export_pdf` 限定在运行目录内，但 MCP 插件权限等同当前用户。
- Docker 构建需要在构建期访问 tessdata 下载 OCR 数据；离线构建需预置 `data/ocr` 并调整 Dockerfile。

## 6. 合规与公平

- 公平性规则基于关键词/正则识别受保护属性并从 JD 中剥离；不能覆盖所有隐晦表达。
- 报告与日志做 PII 掩码；台账保存哈希与路径，不保存明文手机号/邮箱；但运行目录中的原始简历仍是明文，需要靠文件系统权限保护。
- 平台只给建议，不自动拒绝候选人；最终决定必须由 HR 做出并留痕。

## 7. 后续优先级

| 优先级 | 事项 | 原因 |
|---|---|---|
| P1 | 扫描版 PDF 页面渲染 + OCR | 真实简历中扫描件比例高 |
| P1 | 容量池准入与核查输出预算调优（池容量/超时/分段核查） | 饱和与 max-tokens 会实际造成任务失败 |
| P1 | 真实模型质量评测（人工标注 + 重复实验） | 当前只有机制验证 |
| P1 | Web 鉴权与多用户隔离 | 公网/团队使用前提 |
| P1 | 浏览器级 e2e（上传→HITL→报告→证据） | 防止 UI 回归 |
| P1 | 完成后对话工具沙箱/确认（尤其 `python_exec`） | 简历文本可被注入，存在本地执行风险 |
| P2 | 邮箱 IMAP/Exchange 接入 | 减少手工上传 |
| P2 | OCR 版面分析（表格/分栏） | 提升图片简历字段准确率 |
