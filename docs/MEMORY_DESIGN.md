# BoLe 记忆管理实施设计

状态：第一版核心能力已实现，后文含后续设计目标。日期：2026-11-05。

### 当前交付边界

- 已实现 L2 岗位族、不可变评分卡版本（含阈值）、有效期、退役、显式选择及 job 绑定快照。
- 已实现 L3 不可变待审批提案、内容哈希校验、真人入口批准/拒绝/撤回、基线并发保护及事务发布；表单编辑作为草稿，提交后修改需撤回并新建。
- 已实现 L1 任务决策投影、有序消息、带水位/来源哈希的提取式长对话摘要、摘要后的当前 job 原消息读取工具，以及删除来源后的派生清理和规则停用。
- 管理入口为侧栏“岗位与评分标准”。模型工具池只提供当前 job 的只读历史访问，不提供长期规则批准或跨岗位写入工具。
- 第一版摘要使用确定性摘录，不调用 LLM 蒸馏；不保留完整旧对话在提示词内，不宣称摘要无损。最近完整消息和附件可能单独超过预算；后续再加入附件分段读取。
- 尚不提供当前 job 的评估修订分支、自动 Claim 冲突理解、组织身份系统或向量索引。调整已开始任务的标准需新建会话，旧结果保留。

参考：用户提供的 `D:/agent/BoLe_记忆管理设计.md`（v0.3）。本文继承三层显式记忆与人工批准原则，并结合当前代码调整实施范围；不依赖该文档引用的外部产品实现细节。

## 1. 目标与取舍

服务两个需求：同一次招聘任务可靠延续；相似岗位复用经过人工确认的评价标准。记忆必须能解释来源、适用范围、何时生效，以及如何停止使用。

保持三层、五个记忆件：

| 层 | 记忆件 | 权威来源 | 复用边界 |
| --- | --- | --- | --- |
| L1 工作记忆 | 任务事实与决策索引 | 任务台账、证据、决策、运行产物 | 当前 job |
| L1 工作记忆 | 对话上下文摘要 | 有明确范围的聊天记录及来源引用 | 当前 job |
| L2 任务记忆 | 岗位画像与评分卡版本 | 人工确认后的不可变版本 | 同岗位族、显式选择 |
| L2 任务记忆 | 可复用业务参考索引 | 人工维护的知识库、批准的评分卡 | 按角色及岗位族过滤 |
| L3 决策记忆 | 修订提案与审批记录 | HR 纠正及其 Why / How to apply | 先为候选，批准后形成 L2 版本 |

知识库提供参考资料；记忆保存历史任务事实、已确认规则及来源。知识库的 Agent 绑定不代表该角色获得记忆写入权。

第一版不做长期候选人画像库、全自动记忆抽取、自动修改提示词、自动调整权重或开放域经验学习。无需向量数据库；后续可为参考检索增加向量索引，索引不能成为规则生效的依据。

## 2. 当前能力与缺口

已存在：SQLite 任务台账、append-only 事件、原文引用、批次恢复、聊天历史、决策记录、持久化严格审批，以及按 Agent 角色过滤的知识库。

尚缺：统一记忆读写契约、聊天摘要及覆盖水位、跨岗位评分卡版本库、岗位族、修订提案与批准生效事务。

需要纠正的设计假设：

- 当前权威数据由数据库与文件共同组成。事件没有包含全部正文和状态变更信息，不能宣称仅靠 events 重建整个系统。
- 每份简历独立评估，不能把其他候选人摘要注入评估器充当事实。这会引入排序锚定和跨候选人污染。优先压缩完成后长对话。
- 原文保存在文件，台账记录路径；不存在设计文档中假定的 `resumes.raw` 正文列。
- 固定评分卡版本只能保证评价标准及输入可追溯，不能保证云端模型重复生成相同分数或排序。
- 单纯增加两个时间列不等于完整双时间数据库。第一版提供业务有效期和记录时间，不宣称具备任意历史时点查询能力。
- 归档只是会话展示状态，不是保留期管理或物理删除。删除策略必须同时覆盖原文、派生文件、记忆和索引。

## 3. L1：从台账读取，摘要只是可丢弃投影

### 3.1 任务事实索引

提供只读 `JobMemoryView`，聚合当前生效 JD / 评分卡、HR 确认、已提交结果、核查反馈和待处理节点。

不复制完整简历到新记忆表。不通过相似度检索读取其他候选人的事实。重评只读取该候选人对应评估版本的反馈。

来源引用至少包含：`jobId / resumeId / taskId / artifactHash`；引用正文时增加 `documentHash / start / end`。偏移量必须与确定版本的文本绑定，单独保留偏移没有证据意义。

### 3.2 对话摘要

当前 `listChat(..., 40)` 属于截取历史，不能当作摘要机制。新增摘要只作用于长对话的旧区间；最近若干轮完整保留，并预留工具调用和模型输出预算。

触发条件由上下文预算决定，不按每固定轮数强制调用模型。摘要模板沿用五段：岗位与规则、候选人要点、核查状态、HR 决策、待办事项。

关键约束：

1. 使用单调递增的消息序号，保存覆盖起止位置与来源哈希；不使用随机 ID 的大小判断覆盖顺序。
2. 不拆开 assistant 工具调用与 tool 返回组成的消息组。
3. HR 已确认条件直接由结构化决策投影注入，不能只依赖模型摘要保存。
4. 摘要必须携带来源引用，不保留联系方式或无关身份信息。
5. 摘要失败时缩小上下文或按需读取原记录；不得删除原记录或阻塞正常任务恢复。
6. 新摘要可以结合上一摘要生成，但要保留来源集合；重要条件重新从权威台账读取，避免反复压缩造成漂移。

模型摘要作为非权威参考注入，不覆盖 JD、评分卡及原文证据。摘要过期或源数据删除时停止使用，可重建时再生成。

## 4. L2：版本化评价标准，默认不跨岗位自动套用

引入岗位族，例如“支付后端”“前端平台”。岗位族由用户或实施方显式维护，不仅凭模型判断自动归类。

画像和评分卡组成一个版本对象：维度、权重、阈值、适用范围、父版本、业务有效期、创建人、批准人、来源提案和内容哈希。

生命周期：`draft → approved → retired`。批准后内容不可修改；变更创建新版本。退役停止用于新任务，已绑定任务仍读取自己的快照。

新任务流程：

1. 用户选择岗位族；没有岗位族时正常创建独立 JD / 评分卡。
2. 按岗位族、批准状态和有效期检索最多 5 个版本；不匹配可返回空。
3. 画像师展示与当前需求的差异，用户明确选择复用或按当前需求新建。
4. 将选定版本及本次实际评分卡快照绑定到 job；后续发布新版本不能改变此 job。
5. 开始执行后调整评分标准，需要新建评估修订运行；保留前后结果并重新评估受影响候选人，不能只更新权重后混排旧结果。

知识库继续由 `KnowledgeService` 管理，记忆由独立 `MemoryService` 管理。两者可共享文本检索工具，但不共享生效状态。检索来的说明文字不能静默改变已绑定评分卡。

第一版不建设优秀候选人长期画像库，避免把“过去被推荐”反馈为未来评分标准。

## 5. L3：纠正形成提案，批准才影响后续任务

HR 可以从结论或核查节点发起“提出规则修订”，填写规则、Why、How to apply、岗位族及来源。主 Agent 可协助起草，但不能自行批准。

“这个人不应进入推荐名单”首先是候选人级纠正，不自动推导为全岗位规则。只有用户明确希望调整通用标准时，才创建评分卡修订提案。

状态：`draft → pending → approved / rejected / withdrawn`。内容修改必须创建新修订，旧审批不能用于批准新内容。

批准前展示维度和权重差异、适用岗位族、有效期，以及是否影响当前任务。默认仅用于之后的新任务。

批准事务同时完成：校验旧版本仍为预期基线、校验权重与维度、创建新版本、绑定审批记录、更新提案状态、写审计事件。任一步失败全部回滚。并发提案基于过时版本时要求重新审阅，不使用“最后写入覆盖”。

该审批在默认和严格执行模式下都必须真人确认。严格模式的工具授权与长期规则批准是不同授权，不能互相代替；CLI `--yes` 也不能批准长期规则。

被拒绝、未批准及撤回的提案不进入生产评分上下文，可在提案管理页面查看。

## 6. 数据模型

沿用现有台账，新增下列领域表，不建立一个混放事实、规则与摘要的大表：

| 表 | 关键字段 |
| --- | --- |
| `job_families` | id、名称、描述、状态 |
| `scorecard_versions` | id、family_id、version、parent_id、schema_version、profile_json、scorecard_json、content_hash、status、valid_from、valid_to、created_at、approved_by、approval_id |
| `job_policy_bindings` | job_id、evaluation_revision、scorecard_version_id、snapshot_json、snapshot_hash、bound_at |
| `memory_summaries` | id、job_id、from_seq、through_seq、source_hash、summary_json、references_json、model、prompt_version、created_at、status |
| `memory_proposals` | id、revision、family_id、source_job_id、base_version_id、rule、why、how_to_apply、patch_json、source_refs_json、content_hash、status、created_at |
| `memory_conflicts`（后续） | id、job_id、claim_key、left_ref、right_ref、resolution、resolved_by、resolved_at |

扩展 `chat_messages` 的有序消息位置与岗位关联；为审批增加可版本化动作类型 `memory-policy-change`。审批引用提案修订、基线版本和补丁哈希，避免只批准一段无法精确执行的说明文字。

时间字段：规则使用有效区间；工作经历使用结构化开始和结束日期并保留精度与来源；落库时间只表示系统记录时刻。未知时间允许为空，禁止用当前时间补造。

备份至少同时覆盖台账、知识库、原始材料和产物目录。事件继续用于审计，后续若要实现事件重放，应另行定义完整事件契约。

## 7. 服务接口与 Agent 权限

建议目录：`src/memory/`，内含 `service.ts`、`policy-store.ts`、`summarizer.ts`、`proposals.ts`、`types.ts`。

```ts
interface MemoryService {
  getJobView(jobId: string, role: string): Promise<JobMemoryView>;
  recallPolicies(query: PolicyQuery): Promise<PolicyReference[]>;
  summarizeChat(jobId: string): Promise<SummaryResult>;
  proposePolicy(input: PolicyProposalInput): Promise<PolicyProposal>;
  approveProposal(input: ApprovedProposalAction): Promise<PolicyVersion>;
}
```

第一版用显式构建的调用上下文限定 job 和角色，不相信模型自己提供的身份。未来动态 Agent 注册接入能力声明后，仍由服务端执行权限校验。

| 角色 | 可读 | 可写 |
| --- | --- | --- |
| 伯乐 | 当前岗位投影、聊天摘要、批准的规则候选 | 创建提案草稿，不批准 |
| 画像师 | 当前需求、已选评分卡、适用规则参考 | 新岗位画像草稿，不发布版本 |
| 录事 | 当前简历及解析必要上下文 | 当前任务解析结果 |
| 相马官 | 固定评分卡、当前候选人证据、对应核查反馈 | 当前评估结果 |
| 监军 | 当前结论及其来源、固定规则、相关冲突 | 核查结果与冲突记录 |
| 探马 | 文件接入必要信息 | 接入台账，不操作长期记忆 |

角色权限不是完整用户身份认证。当前单机单用户边界保持明确；FDE 可扩展组织命名空间、审批人身份和存储适配器，不把当前方案描述为已具备多租户隔离。

## 8. 界面与 API

不把记忆混入知识库设置。建议新增“岗位与评分标准”页面，提供岗位族、版本历史、提案和引用任务四个视图；Agent 记忆说明放在帮助中。

会话显示本次绑定的评分卡版本，支持跳转来源。收到修订提案时展示“当前值 → 建议值”和 Why，批准与拒绝均可审计。

API 草案：岗位族列表、版本创建/查询/退役、提案创建/提交/撤回、提案审批、job 绑定查询、当前 job 记忆来源查询。版本发布与提案批准使用幂等键及预期基线版本。管理接口不能绕过审批直接将草稿设为 approved。

## 9. 冲突、隐私和删除

多来源对任职年限等事实发生矛盾时，保留两份 Claim 与来源，转人工或等待补充；不把“记录较新”当作“事实更真”。第一版先支持显式纠正和冲突标记，不声称能自动理解全部自然语言矛盾。

姓名、电话和邮箱不进入跨 job 记忆。对岗位描述、Why 等自由文本执行脱敏并人工检查；正则不能保证完全匿名。长期规则禁止引用候选人的敏感身份作为评分条件。

原 job 删除时清理其摘要、私有派生记录和索引。跨 job 已批准规则应在发布时形成独立、脱敏的业务理由，不依赖原始简历正文；删除来源后标记来源已删除，不伪称证据仍可打开。若无法合法保留必要依据，则将规则置为待复核并停止新任务使用。

## 10. 实施顺序与验收

1. **先做 L2**：岗位族、不可变评分卡版本、job 快照绑定与显式选择。收益直接，且是 L3 的生效目标。
2. **再做 L3**：纠正提案、差异展示、真人审批和原子发布，复用审批基础设施。
3. **补 L1**：统一岗位投影及长对话摘要。评估器维持单简历独立上下文，不强加候选人蒸馏。
4. **后续增强**：陈旧提示、显式 Claim 冲突、按需引入向量索引；不承诺“必然越用越准”。

必要验收：

- 新版本发布后，旧 job 的评分卡快照与续跑仍保持原版本。
- 未批准或被拒绝的错误提案，不能改变任何任务评分标准。
- 批准绑定内容哈希；修改补丁后旧批准失效；自动应答不能批准长期规则。
- 两个并发提案不能静默覆盖；发布中途异常不留下半批准版本。
- 岗位族、角色及 job 边界正确，无法读取其他候选人的私有记忆。
- 摘要覆盖范围无遗漏或重复，保留工具消息完整性；摘要丢失可降级，HR 确认条件不丢。
- 来源变化或删除后，引用失效可见，派生数据清理到位。
- 版本快照与审计可重放；真实模型质量提升另用人工标注数据比较，不能由机制测试推导。

交付时分别报告“机制正确性”和“真实筛选质量”，并记录记忆注入内容、引用版本、额外 token 与延迟。
